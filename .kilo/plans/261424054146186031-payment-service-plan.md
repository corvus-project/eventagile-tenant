# Payment Service Plan for Subscription Renewal

## Context

The subscription system has a `RenewSubscription` console command and an `AccountSetup` command, but neither processes payments. We need to add a fake payment service so renewal and setup actions are validated against a payment gateway before proceeding. Since this is a side project, we'll simulate payments (no real gateway) but design the architecture so swapping in a real provider later is a one-line change.

## Important Details

- **No real payment gateway** — a fake driver that simulates Stripe-like behavior (success, failure, decline).
- **15-day free trial** — handled entirely in code via `trial_ends_at` on the subscription model. Stripe supports trials natively, but since we fake payments, we simulate trial as a code-level period where `isActive()` returns true but no charge occurs.
- **AccountSetup** has two actions: `SETUP` (new tenant) and `RESETUP` (remove + recreate). Payment is only called on `SETUP`.
- **RenewSubscription** processes subscriptions where `status='active'` AND `ends_at <= now()`. Payment must succeed before the renewal record is created.

| `app/Models/PaymentTransaction.php` | Model + migration to record every payment attempt (charge, refund, status, gateway response). |
| `database/migrations/2026_09_14_000000_create_payment_transactions_table.php` | Migration for `payment_transactions` table. |
| `database/seeders/PaymentTransactionFactory.php` | Factory for test data. |

### Interface Methods (`PaymentService`)

```php
interface PaymentService
{
    /**
     * Charge a customer. Returns ['success' => bool, 'transaction_id' => string, 'message' => string, 'amount' => decimal, 'metadata' => array].
     */
    public function charge(string $customerId, float $amount, string $currency, array $metadata = []): array;

    /**
     * Refund a transaction. Returns similar result array.
     */
    public function refund(string $transactionId, float $amount = null): array;

    /**
     * Get status of a transaction by ID.
     */
    public function getStatus(string $transactionId): array;

    /**
     * Return the last gateway response for debugging/logging.
     */
    public function getLastResponse(): ?array;
}
```

### Fake Gateway Behavior

- `charge()` always succeeds by default (100% success rate)
- If `APP_PAYMENT_FAIL_RATE` env var is set (e.g. `0.2`), randomly fails that percentage of charges
- On failure: returns `['success' => false, 'transaction_id' => null, 'message' => 'Card declined', ...]`
- On success: returns `['success' => true, 'transaction_id' => 'txn_xxx', 'message' => 'Payment successful', 'amount' => 9.99, 'metadata' => [...]]`
- `refund()` marks transaction as `refunded`, returns success
- `getStatus()` returns `pending` / `succeeded` / `failed` / `refunded`
- All transactions are logged to `PaymentTransaction` model (tenant-scoped)
- Respects a configurable grace period for retries before hard failure

## Phase 2 — Integrate Payment into Subscription Renewal

### Modify: `app/Console/Commands/RenewSubscription.php`

**Current flow:**
```
Find expired active subs → call $subscription->renew() → log result
```

**New flow:**
```
Find expired active subs → for each:
  1. Get tenant's active subscription
  2. Call PaymentService::charge() with:
     - customer_id: $subscription->stripe_customer_id
     - amount: $subscription->amount
     - currency: $subscription->currency
     - metadata: ['subscription_id' => $subscription->id, 'tenant_id' => $tenant->id]
  3. If payment succeeds:
     a. Log PaymentTransaction (status: succeeded)
     b. Update subscription fields:
        - last_payment_date = now()
        - last_payment_status = 'succeeded'
        - payment_gateway = 'fake'
     c. Call $subscription->renew() (creates new record, marks old as expired)
     d. Create new PaymentTransaction for the renewal charge
  4. If payment fails:
     a. Log PaymentTransaction (status: failed)
     b. Update subscription fields:
        - last_payment_status = 'failed'
        - renewal_status = 'payment_failed'
     c. Send notification (log warning, no actual notification yet)
     d. Skip renewal — tenant keeps grace period access
```

### Modify: `app/Models/Subscription.php`

Add a `renewWithPayment()` method that wraps the current `renew()` with payment logic:

```php
public function renewWithPayment(PaymentService $payment): bool
{
    return DB::transaction(function () use ($payment) {
        $paymentResult = $payment->charge(
            $this->stripe_customer_id,
            $this->amount,
            $this->currency,
            ['subscription_id' => $this->id, 'tenant_id' => $this->tenant_id]
        );

        if (! $paymentResult['success']) {
            $this->last_payment_status = 'failed';
            $this->renewal_status = 'payment_failed';
            $this->save();
            return false;
        }

        // Log successful payment
        $this->last_payment_date = now();
        $this->last_payment_status = 'succeeded';
        $this->payment_gateway = 'fake';
        $this->save();

        return $this->renew();
    });
}
```

The existing `renew()` method stays unchanged (pure DB logic). `RenewSubscription` command calls `renewWithPayment()` instead.

### Add Renewal Status Values

The `renewal_status` field currently uses `completed`. Add new values:
- `payment_failed` — payment was declined during renewal
- `pending` — renewal is in progress (payment processing)

## Phase 3 — Integrate Payment into AccountSetup

### Modify: `app/Console/Commands/AccountSetup.php`

**Current flow for SETUP:**
```
Create tenant → fire OnboardTenant event → mark FINISHED
```

**New flow for SETUP:**
```
Create tenant → for SETUP action only:
  1. Determine the tenant's plan (from $account->config['plan'] or default)
  2. Calculate the trial period (15 days from now)
  3. Call PaymentService::charge() for the initial subscription:
     - If SUCCESS: proceed to create subscription record (see below)
     - If FAILURE: log error, mark account action as 'SETUP_FAILED', send notification, skip
  4. Create Subscription record:
     - status = 'active'
     - trial_ends_at = now() + 15 days
     - starts_at = now()
     - ends_at = now() + 15 days (trial period)
     - amount = plan price
     - currency = plan currency
     - interval = plan interval
     - interval_count = plan interval_count
     - plan_name, plan_description, plan_id from plan data
     - plan_limitations = plan limitations
     - payment_gateway = 'fake'
     - payment_method = 'card_xxx' (from config or fake)
     - next_billing_date = trial_ends_at + 1 day (or after trial ends)
     - last_payment_date = now()
     - last_payment_status = 'succeeded'
     - status = 'active'
  5. Fire OnboardTenant event (unchanged)
  6. Mark account action as FINISHED

For RESETUP action:
  - No payment called (same as current — remove tenant, recreate)
  - But: if the new tenant gets a subscription, it should be a fresh trial again
```

### Subscription Creation Helper

Add `SubscriptionService::createSubscriptionForTenant(Tenant $tenant, Plan $plan, PaymentService $payment): array` method that:
1. Calls payment for the plan's price
2. Creates the subscription record if payment succeeds
3. Returns `['success' => bool, 'subscription' => ?Subscription, 'error' => ?string]`

## Phase 4 — 15-Day Free Trial Refactoring

### Question: Does Stripe support trial periods?

**Yes.** Stripe supports trials natively via `trial_end` when creating subscriptions. In our code, we already have `trial_ends_at` on the `Subscription` model.

### Do we need code refactoring for trials?

**Minimal refactoring needed.** The `trial_ends_at` field already exists and is already in `$fillable`. The `isActive()` method already considers `starts_at`/`ends_at`. The key changes:

### Modify: `app/Models/Subscription.php` — `isActive()` method

**Current behavior:** A subscription is active if `status` is in `['active', 'cancelled', 'canceled']` AND `ends_at` is within grace window.

**New behavior:** During the trial period (`trial_ends_at` is in the future), the subscription is active regardless of `ends_at` and `status`. After trial ends, normal rules apply.

```php
public function isActive(): bool
{
    // During trial period, always active
    if ($this->trial_ends_at && now()->lt($this->trial_ends_at)) {
        return true;
    }

    // Trial has expired — apply normal rules
    if (! $this->isAccessibleStatus()) {
        return false;
    }

    $now = now();
    if ($this->starts_at && $now->lt($this->starts_at)) {
        return false;
    }
    if ($this->ends_at && $now->gt($this->ends_at)) {
        $graceHours = (int) config('tenancy.subscription.renewal_grace_hours', 24);
        if ($now->gt($this->ends_at->copy()->addHours($graceHours))) {
            return false;
        }
    }

    return true;
}
```

### Modify: `app/Services/SubscriptionService.php` — `accessSite()` and all private methods

Add a `isInTrial()` check helper:
```php
private function isInTrial(Subscription $sub): bool
{
    return $sub->trial_ends_at && now()->lt($sub->trial_ends_at);
}
```

In `accessSite()`, `createEvent()`, `canRegister()`, `sendEmails()`:
- If in trial: allow access, but mark response with `'trial' => true, 'trial_ends_at' => $sub->trial_ends_at`
- Limits still apply during trial (configurable per plan)
- Email sending and registration limits are enforced even during trial

### Modify: `RenewSubscription` command

For subscriptions in trial:
- Do NOT charge during trial period (the `trial_ends_at` hasn't passed yet)
- When `trial_ends_at` is reached and `ends_at` has passed, THEN charge and renew
- Update the command logic: skip subscriptions where `trial_ends_at > now()` (still in trial)

### Seed Plan Data

Update `PlanSeeder` to set `price = 0` for the trial plan (or keep the normal price but skip charging during trial). The trial plan should have:
- `interval` = 'month'
- `interval_count` = 1
- `price` = 0.00 (or actual price if trial is just a code-level period)
- `limitations` = same as other plans

## Trial Period: Stripe vs Code-Level Decision

**Stripe supports trials natively** via `trial_end` on subscription creation. However, since we're building a fake gateway, the trial is a code-level concept. The `trial_ends_at` field already exists in the schema. We don't need to restructure anything — just:

1. Make `isActive()` honor `trial_ends_at`
2. Skip payment charges during trial
3. Set `trial_ends_at` to 15 days from signup during onboarding
4. After trial ends, normal renewal cycle begins with payment

This keeps the codebase ready to swap in Stripe later with minimal changes — the `PaymentService` interface abstracts the gateway, and trial logic is independent of payment processing.
